## 1. 오래 쓰는 사용자

시스템 시각을 건드리는 대신 **기록의 시각을 과거로 심어** 들어갔다.
0 / 1 / 7 / 21 / 120 / 400일 전, 그리고 미래(-5일).

### ★ 찾은 것 — 해를 넘기면 날짜가 모호해진다

400일 전 기록으로 들어가니 [이어서 하기] 카드가 **"7월 27일"** 이라고만 적었다.
120일 전은 **"5월 3일"**. 올해인지 작년인지 알 방법이 없다.

한 번에 끝나는 서비스라면 문제가 아니다. 그런데 이 서비스는 그렇지 않다.
법령에 처리 기한이 없어서 회신이 언제 올지 모르고, 우리 화면도 그래서
카운트다운 대신 경과일만 적는다. 몇 달 뒤에 돌아오는 것이 정상 동선이다.

**고침** — `formatWhen` · `formatDate` 가 **해가 다를 때만** 연도를 붙인다.
같은 해면 그대로다(짧은 표기를 잃지 않는다).

```
400일 전 → "2025년 7월 27일 22:14"   (전: "7월 27일 22:14")
  2일 전 → "8월 29일 22:14"          (그대로)
```

12월 31일 → 1월 1일처럼 **하루 차이로 해가 갈리는 경우**도 시험에 넣었다.

### 미래 시각이 들어 있으면

기기 시계가 어긋났거나 손으로 고친 파일에서 생긴다.
`daysSince()` 는 음수를 `null` 로 돌려주므로 **"○일 지났습니다"를 아예 적지 않는다.**
날짜만 그대로 보인다. 없는 사실을 만들지 않는 쪽이라 그대로 둔다.

### 기록이 커지면

정정 행 60건 + 회신 항목 20건 + 서식 2를 다섯 벌 + 긴 값으로 **71KB** 짜리 기록을 만들어
여섯 화면에 각각 들어갔다. **오류 경계 0건, 처리되지 않은 예외 0건.**
저장·복원 후 크기도 그대로였다(정규화가 값을 깎지 않는다).

### 낯선 스키마 버전의 파일

`schemaVersion` 을 0 / 2 / 99 / null / "2" / -1 / 1.5 로 바꿔 불러왔다.
**전부 이유를 말하고 거절한다.** 조용히 무시하거나 반쯤 불러오는 경우가 없었다.

| 넣은 값 | 화면이 말한 것 |
|---|---|
| 2 · 99 · "2" · 1.5 | ✕ 더 새로운 버전(N)에서 내보낸 파일입니다. 이 화면을 새로고침해 최신 버전으로 다시 시도해 주세요. |
| 0 · null · -1 | ✕ 파일의 형식 버전을 읽을 수 없습니다. 파일이 손상된 것 같습니다. |

거절된 뒤 저장소는 손대지 않은 채로 남는다(불러오기 실패가 기존 기록을 지우지 않는다).

### 같은 사람이 여러 기관에 각각

기본 건에 값을 적고 → CB사 건을 추가 → 건을 오갔다.
**기본 건의 값이 그대로 남아 있었다.** 건별 작성 내용은 따로 저장된다
(`form.form1` / `form.second.form1`). 예외 0건.

### 서식 2 여러 벌의 상한 (보고만)

`MAX_FORM2_EXTRAS = 4`. 화면은 4벌에 이르면 [추가] 버튼을 감추므로 **손으로 만들 때는
넘길 수 없다.** 다만 5벌 이상이 든 파일을 불러오면 **말없이 4벌로 잘린다.**

고치지 않는 이유: 여기에 안내를 붙이려면 불러오기 경로에 경고 상태를 하나 더 만들어야 하고,
그 경로는 지금 "성공/실패" 두 가지로 단순하다. 실제로 걸릴 사람이 거의 없는 것을 위해
불러오기를 복잡하게 만드는 쪽이 더 위험하다. 대신 이 문서에 적는다.

## 3. ★ 사건 유형 × 업권 전수 — 판정이 근거 조문과 모순되는가

지금까지의 시험은 대표 조합 몇 개만 봤다. 이번엔 **전부** 돌렸다.
`resolveTransactionBasis()` 는 순수 함수라 브라우저가 필요 없다 — `tests/tmatrix.mjs`.

- 사건 7종(5 + `null` + 없는 값) × 업권 18종(15 + 빈 값 + `null` + 없는 값) × 한도 4종
  = **504 조합**, 검사 **4,042항목**.

무엇을 모순으로 봤는가:

- 특정됐다면서 근거가 상위 문구(가목 본문)뿐인 경우
- 특정 못 했다면서 하위 호(가목 N)를 근거로 든 경우
- 화면에 보이는 이름이 근거로 든 호의 이름과 다른 경우
- 위임 경로(`basisChain`)가 실제 근거 두 조문을 담지 않는 경우
- "한 번 더 묻는다"가 물어볼 질문이 없는 자리에서 뜨는 경우,
  또는 물어본 답이 판정을 끝내지 못하는 경우

**결과: 모순 0건.** 위임(가목 4) → 시행령 제2조 제6항)은 저축은행·신협·보험 세 업권에서만
나오고, 그때만 `basisChain` 이 붙는다. 그 밖의 업권은 하위 호를 특정하지 않고
상위 문구만 표시한다 — 회피가 아니라 정확한 판단이라는 코드 주석과 실제가 일치했다.

권리 5종도 상대방(CB/FI)별로 훑어 **항 번호와 근거 조문이 어긋나는 항목이 없음**을 확인했다.

## 5. 되돌리기

### ★ 찾은 것 1 — 진단을 바꿔도 /strategy 는 옛 목록을 "지금 것"처럼 말했다

**시도**: 상황 서술을 적고 → AI 후보를 받고 → 진단으로 돌아가 서술을 **완전히 다른 내용**으로
바꾼 뒤 → 주소창으로 `/strategy` 에 다시 들어갔다.

**결과**: 옛 후보가 그대로 있고, 화면은 여전히
**"적어주신 상황을 읽고 고른 목록입니다"** 라고 말했다.
각 항목의 선정이유는 `'프리랜서로 3년'` 을 인용하는데, 지금 진단에는 그 말이 없다.

`/diagnose` 쪽에는 이미 좋은 안내가 있다 — "진단을 바꾸셨습니다 … 지금 상황과 맞지 않을 수
있습니다" + [전략 후보 지우고 다시 만들기]. 그런데 **그 화면을 거치지 않고** 네비게이션이나
주소로 바로 `/strategy` 에 들어가면 아무 말도 없었다.

이 서비스의 차별점은 "인용을 서버가 사용자 원문과 대조한다"이다.
그 인용이 지금 화면의 서술과 어긋나 보이면, 그 주장까지 함께 흔들린다.

**고침**:
- 후보를 만들 때 **무엇을 읽고 만들었는지**를 함께 남긴다
  (`strategy.basedOn = { reason, eventId, institutionSectorId }`).
- 지금 진단과 다르면 목록 위에 밝힌다 —
  *"진단을 바꾸신 뒤의 목록입니다 … 지금 진단에 적혀 있는 상황이 아니라, 그 전에 적으셨던
  서술을 읽고 만든 것입니다."* [다시 만들기]는 원래 있던 버튼이다.
- **`basedOn` 이 없는 옛 기록에는 붙이지 않는다.** 무엇으로 만들었는지 모르는 것을
  "낡았다"고 단정하지 않는다. 샘플 캐시·일반 목록도 대상이 아니다.

### ★ 찾은 것 2 — 모르는 분류의 정정 행이 조용히 사라졌다

섹션 2 표는 법이 정한 다섯 분류(식별 / 거래내용 / 신용도 / 신용거래능력 / 기타)만 그린다.
그 다섯에 없는 `categoryId` 가 붙은 정정 행은 **저장소에는 남아 있는데 표에는 나타나지 않았다.**
사용자는 자기가 표시한 항목이 어디로 갔는지 알 수 없다.

정상 경로에서는 생기지 않는다(`buildCorrectionRows()` 가 언제나 다섯 중 하나로 귀속시킨다).
손으로 고친 저장소, 남이 만든 파일, 또는 앞으로 분류 id 가 바뀔 때 생긴다.

**고침** — 정규화가 모르는 분류를 **기타 정보**로 보낸다. 정상 경로의 결과는 그대로다
(다섯 중 하나면 통과). 내용도 분류도 없는 빈 행은 여전히 버린다.

### ★ 찾은 것 3 — 저장소를 거쳐 들어온 "거절"을 다시 검사하지 않았다

서버(`api/interpret.js applyInterpretGuards`)는 **"세 유형을 모두 설명한 회신은 거절일 수
없다"**를 강제한다. 법 제36조의2 제3항의 거절은 요구 자체에 응하지 않은 것이기 때문이다.
그런데 **저장소와 불러온 파일은 그 경로를 거치지 않는다.**

**고침** — 복원할 때 같은 검사를 건다. 거절 사유라던 문장은 버리지 않고 법정 제외
(시행령 제31조의2 제8항 제3호 단서) 쪽으로 옮긴다 — 서버와 같은 처리다.
**서버를 거친 값은 이미 이 조건을 만족하므로 정상 경로의 결과는 달라지지 않는다.**

### 그 밖의 되돌리기 — 문제 없었다

| 시도 | 결과 |
|---|---|
| 진단을 바꾸면 이후 단계가 어떻게 되는가 | **지우지 않는다.** 무엇이 남아 있는지 이름으로 알려주고, 지울지는 사용자가 정한다 |
| 상대방을 CB 로 바꾸면 | 업권이 비워진다(CB 에는 업권 개념이 없다). 나머지는 유지 |
| 서식 작성 중 회신 해석에 갔다가 돌아오면 | 성명·요청 항목 그대로. 해석 결과도 복원 |
| 입력 직후 200ms 만에 새로고침 | **값이 남는다.** `pagehide`·`visibilitychange` 에서 대기 중이던 저장을 밀어 넣는다 (200/600/1200/2000ms 네 경우 모두 확인) |

## 6. 확인한 것 / 확인하지 못한 것

확인한 것 (숫자는 이번에 잰 것):

- 여섯 화면 순회 시 **외부 호스트 요청 0건** (웹폰트·분석도구·CDN 없음)
- 71KB 기록으로 전 화면 진입 — 오류 경계 0, 예외 0
- 판정 조합 504가지 · 검사 4,042항목 — 모순 0
- 회귀 33종 통과, 인쇄 쪽수 예고=실제 10/10, 값 잘림 42/42

확인하지 못한 것:

- **실제 시스템 시계를 되돌린 상태**로는 돌려보지 않았다. 기록의 시각을 과거로 심는 방식을 썼다.
  화면이 읽는 것은 기록의 시각과 `new Date()` 뿐이라 같은 조건이지만, 같지 않을 여지는 남는다.
- **몇 주에 걸친 실제 사용**은 여전히 없다. 이 서비스로 만든 서류를 내고 회신을 받아 본
  사례가 없다는 사실은 그대로다 (`docs/facts.md` §7).
- 두 탭 동시 진행의 덮어쓰기는 이번에도 고치지 않았다. 저장 경로를 건드리는 회귀 위험이
  이득보다 크다고 보고, 앞선 감사의 판단을 유지한다.
