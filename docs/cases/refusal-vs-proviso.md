# 사례 기록 — AI가 "거절"과 "법정 제외"를 혼동했고, 서버의 논리 검증이 차단했다

발생: 2026-08-23, `/api/interpret` 실제 API 호출 검증 중
관련 코드: `api/interpret.js`, `src/data/law.js`(`RESPONSE_DISPOSITIONS`, `BASE_INFO_KEYWORD_RULES`)

---

## 1. 무슨 일이 있었나

### 입력

3유형(결과·주요 기준·기초정보의 개요)을 모두 설명하고, 마지막에 다음 문장이 붙은 회신문.

> 각 정보의 결합 방식은 당사가 자체 개발한 모델에 해당하여 제공 대상에서 제외됩니다.

### AI의 출력

```json
{
  "covered": ["result", "criteria", "baseInfo"],
  "missing": [],
  "refused": true,
  "refusalReasonText": "각 정보의 결합 방식은 ... 제공 대상에서 제외됩니다."
}
```

### 무엇이 틀렸나

**"제외"를 "거절"로 판정했다.** 이 둘은 근거 조문도, 법적 성격도, 사용자가 취해야 할
대응도 전혀 다르다.

| | A. 거절 | B. 설명 범위의 법정 제외 |
|---|---|---|
| 근거 | 법 제36조의2 제3항 | 시행령 제31조의2 제8항 제3호 단서 |
| 성격 | 요구 **자체에 응하지 않음** | 요구에는 **응하면서** 가공·추론 정보만 뺌 |
| 예 | "동일 거래에 3회 이상 반복 요구하셨으므로 응할 수 없습니다" | "가중치 산정 방식은 자체 개발·가공한 정보이므로 제공 대상에서 제외됩니다" |
| 사용자의 다음 행동 | 거절 사유의 법정 근거를 확인 | **정상 회신**이므로 받은 내용으로 다음 단계 진행 |

위 입력은 명백히 B다. 금융회사는 요구에 응했고, 법이 제외를 허용한 부분만 빼고 다 줬다.

### 실제 피해

이 서비스는 판정 결과로 **사용자의 다음 행동을 결정**한다(`decideNextAction`).
`refused: true`는 사용자를 "거절 사유를 확인하세요" 분기로 보낸다.
정상적으로 회신받은 사용자가 "나는 거절당했다"고 오인하게 된다.
법률 도메인에서 이런 오분류는 단순한 표시 오류가 아니라 **잘못된 권리 행사로 이어지는 오류**다.

## 2. 왜 이런 일이 생기나

두 개념 모두 자연어로는 "안 준다"로 읽힌다. LLM은 회신문의 **표면 어휘**("제외",
"제공 대상 아님", "자체 개발")를 보고 거절로 분류했다. 조문 구조상 두 개념이 다르다는 것은
법령을 알아야 판별되는 사실이며, 문장 표면에는 드러나 있지 않다.

이것은 프롬프트가 부족해서 생긴 문제이면서, 동시에 **프롬프트만으로는 보장할 수 없는 문제**다.
프롬프트를 아무리 정교하게 써도 다음 호출에서 같은 오류가 나지 않는다는 보장이 없다.

---

## 3. 어떻게 막았나 — 3중 방어

### (1) 프롬프트 — 두 개념을 조문과 함께 명시

`api/interpret.js`의 시스템 프롬프트에 A/B를 각각 근거 조문·정의·예문과 함께 주입했다.
문구는 AI가 아니라 `src/data/law.js`의 `RESPONSE_DISPOSITIONS`에서 읽는다.

> "제외", "제공 대상이 아님", "자체 개발", "자체 가공", "산출"이라는 표현은
> 그 자체로 거절이 아닙니다. B입니다. refused 를 true 로 하지 마십시오.
> 회신이 세 유형에 모두 답하고 있다면 그것은 어떤 경우에도 거절이 아닙니다.

출력 스키마에 `excludedByProviso`(boolean)와 `provisoText`(string)를 추가해,
B를 **버리지 않고 B로 표현할 자리**를 만들었다.

### (2) ★ 서버의 논리 검증 — 이것이 핵심이다

프롬프트는 부탁이고, 가드는 판정이다. `applyInterpretGuards`에 다음을 넣었다.

```js
// 법 제36조의2 제3항의 "거절"은 요구 자체에 응하지 않은 것이다.
// 세 유형을 모두 설명했다면 요구에 응한 것이므로 거절일 수 없다.
if (refused && missing.length === 0) {
  refused = false
  if (refusalReasonText) {
    if (!provisoText) provisoText = refusalReasonText
    excludedByProviso = true
    refusalReasonText = ''
  }
}
```

AI가 `refused: true`라고 해도, **covered가 3유형을 모두 포함하면 코드가 false로 뒤집는다.**
그리고 AI가 거절 사유라며 넘긴 원문을 버리지 않고 `provisoText`로 옮긴다.
정보는 보존하되 **법적 성격만 코드가 다시 붙인다.**

### (3) 다음 행동 판정에서 분리

`decideNextAction`은 `excludedByProviso`를 **보지 않는다.** 의도적이다.
법정 제외는 정상 회신이므로 거절 분기가 아니라 "확인이 끝났습니다"(유리한 정보 제출) 분기로 간다.

### (4) 사용자에게는 오히려 더 설명한다

제외가 실제로 적용된 회신이면 결과 화면의 "제도의 한계" 박스를 강조하고,
회신 원문을 인용한 뒤 "이것은 요구를 거절한 것이 아닙니다"를 명시한다.
사용자가 그 단서를 실제로 적용받은 순간이므로, 설명이 가장 필요한 순간이다.

## 4. 같은 호출에서 발견된 두 번째 오류 — 5분류 오분류

AI가 "직업"을 **식별정보**로, "건강보험 납부"를 **기타 정보**로 분류했다.

- 법 제2조 제1호의5는 "개인의 직업ㆍ재산ㆍ채무ㆍ소득의 총액 및 납세실적"을
  **신용거래능력 판단정보**로 정의한다. 직업은 여기 속한다.
- 식별정보(법 제2조 제1호의2)는 성명·주소·전화번호·개인식별번호·생체정보뿐이다.
- 건강보험 납부실적은 서식 2가 R3 예시로 직접 든 항목이다.

분류는 **정정 요구의 근거**가 되므로 틀리면 서식에 잘못된 조문이 인쇄된다.

### 대응

1. 프롬프트에 5분류의 **법정 정의와 법이 든 예시를 전부 주입**했다
   (`BASE_INFO_CATEGORIES`의 `definitionBasis`, `examples`를 그대로 사용).
   분류명만 주고 알아서 판단하게 두지 않는다.
2. 조문이 직접 열거한 단어에 한해 코드가 보정한다(`BASE_INFO_KEYWORD_RULES`).
   과하게 하드코딩하지 않는다. 규칙에 걸리지 않는 항목은 AI 분류를 그대로 둔다.
   순서가 의미를 가진다 — "채무 불이행"(1호의4)이 "채무"(1호의5)보다 먼저 평가된다.
3. **보정된 항목은 화면에서 사용자가 직접 바꿀 수 있다.** 어떤 분류에서 무슨 근거로
   바뀌었는지 함께 표시한다. 분류는 정정 요구의 근거이므로 최종 판단은 사용자 몫이다.

## 5. 검증 결과

|---|---|---|
| 3유형 전부 설명 + "결합 방식은 자체 개발 모델이라 제외" | `refused: true` ❌ | `refused: false`, `excludedByProviso: true` ✅ |
| "동일 거래 3회 이상 반복 요구하셨으므로 응할 수 없습니다" | — | `refused: true` ✅ |

실제 API 호출 및 브라우저 클릭 테스트로 두 케이스가 서로 다른 분기로 가는 것을 확인했다.

## 6. 이 사례가 말하는 것

> **법정 사실은 결정론적으로, 사용자 맥락 해석만 LLM으로.**

이 프로젝트의 절대 규칙(`CLAUDE.md`)은 처음부터 "법조문을 LLM이 생성하지 않는다"였다.
이 사례는 그 규칙이 **한 발 더 나가야 한다**는 것을 보여준다.

LLM이 법조문 텍스트를 만들지 않더라도, **법적 개념을 잘못 적용**할 수 있다.
조문 텍스트를 상수로 박는 것만으로는 부족하고,
**AI의 판정 결과가 법 구조와 모순되는지를 코드가 검산**해야 한다.

여기서는 "3유형을 다 설명했으면 거절일 수 없다"는 것이 법 구조에서 따라 나오는 명제였고,
코드가 그 명제로 AI의 출력을 뒤집었다.

AI가 뭐라 하든 **코드가 판정한다.**
