# 적대적 사용 감사 — 2026-08-30

지금까지의 감사는 **정상 경로**를 봤다. 이번에는 이상하게 쓰는 사람을 상정했다.
심사위원은 아무거나 눌러 보는 사람이고, 거기서 깨지면 그게 인상을 결정한다.

대상은 **로컬 빌드본**(`npm run build` → `vite preview :4400`)이다.
배포본과 소스는 같지만, 아래 결과 중 **수정 이후의 것들은 아직 배포되지 않았다**.

## 판정 기호

| 기호 | 뜻 |
|---|---|
| OK | 죽지 않고, 사용자에게 개발자 오류가 보이지 않고, 이전 입력이 남아 있다 |
| BOUNDARY | 화면이 오류 경계로 넘어갔다 (서비스는 살아 있지만 그 화면은 못 쓴다) |
| DEAD | 빈 화면 |
| OVERFLOW | 죽지는 않지만 **입력한 값이 인쇄물에서 잘려 나간다** |
| DUP | 요청이 중복으로 나간다 |
| INFO | 결함이 아니라 알아 둘 사실 |

## 1. 고친 것

### ① AI 호출 버튼 연타 → 요청이 누른 만큼 나갔다

**시도**: `/strategy` 의 [제출할 정보 후보 만들기] 를 15회 연달아 클릭.
**결과**: `/api/analyze` 요청 **15회**.

버튼은 `state` 가 `'loading'` 이 되면 화면에서 사라진다. 그런데 그건 **다시 그린 뒤**의 일이다.
같은 프레임 안에서 연달아 눌리면 그만큼 요청이 나간다.
심사기간에는 실제 API 키가 붙어 있으므로 그대로 비용이고, 요청 한도에도 닿는다.
더 나쁜 것은 **늦게 온 옛 응답이 새 응답을 덮어쓸 수 있다**는 점이다.

**조치**: `useRef` 로 진행 중 표시를 두고, 진행 중이면 새 호출을 내보내지 않는다.
`/strategy` 와 `/response` 두 곳 모두. (`src/pages/Strategy.jsx`, `src/pages/Response.jsx`)

### ② 폴백 사유를 사실과 다르게 말하고 있었다

**시도**: `/api/analyze` 가 200 을 주면서 본문은 JSON 이 아닌 HTML 을 돌려주게 가로챘다.
**결과(고치기 전)**: 화면이 **"응답이 지연되어 기본 목록을 보여드립니다."**

지연된 적이 없다. 본문을 해석하지 못한 것이다. 연결이 끊겼을 때도 같은 문장이 나왔다.
어떤 실패든 `catch` 에서 `fallback('timeout')` 으로 흡수하고 있었기 때문이다.
이 서비스는 화면에 사실만 적는다는 규칙을 스스로 어기고 있었다.

**조치**: 중단(`AbortError`)과 그 밖의 실패를 구분한다. 본문 파싱 실패는 따로 잡는다.
(`src/lib/analyze-client.js`, `src/lib/interpret-client.js`)

**고친 뒤** — 같은 시도를 다시 했을 때 화면이 말하는 것:

| 주입한 고장 | 화면 문구 |
|---|---|
| 200 + HTML 본문 | 응답을 해석하지 못해 기본 목록을 보여드립니다. |
| 200 + 스키마 불일치 | 적합한 제안을 얻지 못해 기본 목록을 보여드립니다. |
| 500 + HTML 본문 | AI 연결이 일시적으로 어려워 기본 목록을 보여드립니다. |
| 429 | 요청이 많아 기본 목록을 보여드립니다. |
| 응답 중간 절단 | AI 연결이 일시적으로 어려워 기본 목록을 보여드립니다. |
| 26초 뒤 응답 (한도 25초) | 응답이 지연되어 기본 목록을 보여드립니다. |

모든 경우에 **후보 목록은 그대로 나오고**, `※ 일반 목록입니다` 배너가 함께 뜬다.

### ③ 띄어쓰기 없는 긴 값이 인쇄물에서 잘려 나갔다 — 가장 나쁜 종류

**시도**: 서식 1 의 [성명] 칸에 여러 종류의 긴 값을 넣고 실제로 A4 로 인쇄(printToPDF)해
글자 수를 셌다.

| 넣은 값 | 인쇄된 글자 수 | 판정 |
|---|---|---|
| 띄어쓰기 있는 한글 200자 | 전부 | ok |
| **띄어쓰기 없는 한글 200자** | **163자** | **잘림** |
| **120자 URL** | 잘림 | **잘림** |
| 5000자 한 단어 | **230자** | **잘림** |

**입력한 값이 조용히 사라진 채 법정 서식이 출력됐다.** 화면은 "1페이지로 출력됩니다"라고만 말했다.

원인은 두 가지가 겹친 것이다.

1. `body` 에 `word-break: keep-all` 이 걸려 있다. 한국어 단어가 중간에서 끊기는 것을 막으려고
   일부러 넣은 규칙인데, 그 아래에서는 **띄어쓰기 없이 쓴 긴 값이 한 덩어리**로 취급된다.
2. 값 칸의 `break-words`(`overflow-wrap: break-word`)는 **줄바꿈만 허용**할 뿐
   표의 최소 너비(min-content)를 줄이지 못한다.

그래서 끊어질 곳이 없는 값이 들어오면 표가 종이 밖으로 밀려 나가고, 나간 부분은 인쇄되지 않는다.

**조치**: `.sheet-value` 클래스를 만들어 **사용자가 넣은 값이 그려지는 자리에만**
`word-break: break-all` + `overflow-wrap: anywhere` 를 준다.
서식의 고정 문구와 라벨은 그대로 둔다 — 거기서 단어가 끊기면 서식이 이상해진다.
(`src/index.css` 의 `.sheet-value`, `src/pages/Document.jsx` 의 `Field` · `Blank`)

처음에는 표 칸(`td`) 전체에 `overflow-wrap: anywhere` 만 줬는데, **그게 회귀를 냈다.**
인쇄는 고쳐졌지만 측정용 숨은 영역은 `keep-all` 아래에서 여전히 안 줄어들어
`phase8` 의 "큰글씨/긴이름"에서 **예고 2쪽 / 실제 1쪽**이 됐다. 회귀 시험이 잡았다.
값 칸에 `break-all` 을 함께 주고 나서 인쇄와 측정이 같아졌다.

**고친 뒤 재측정**:

| 넣은 값 | 인쇄된 글자 수 |
|---|---|
| 띄어쓰기 없는 한글 200자 | **전부** |
| 5,000자 한 단어 | **전부** |

- `phase8` 서식 1 쪽수 6가지 조합 **전부 예고 = 실제**
- `run-print.sh` 서식 2 쪽수 10가지 조합 **전부 예고 = 실제**
  (값이 더 촘촘히 접히면서 몇몇 조합의 쪽 수 자체가 줄었다 — 예고도 함께 줄어 맞는다)

### ④ 저장소·불러온 파일이 오염되면 화면이 오류 경계로 넘어갔다

**시도**: `localStorage` 를 손으로 오염시킨 상태에서 6개 경로에 각각 들어갔다(18가지 오염).

| 오염 | 결과(고치기 전) |
|---|---|
| `interpretation` 의 필드 타입을 뒤집음 (`covered:'x'`, `baseInfoItems:'y'`) | `/response` 오류 경계 |
| `baseInfoItems` 원소가 객체가 아님 | `/response` 오류 경계 |
| `strategy.candidates` 의 필드가 객체 | `/strategy` 오류 경계 |

`normalizeJourney()` 가 **얕았다.** `isObj()` 만 확인하고 안의 값은 그대로 통과시켰다.
React 는 객체를 자식으로 받으면 렌더 도중 예외를 던진다.
서버(`api/interpret.js`)에는 가드가 있지만, **저장소와 불러온 파일은 그 경로를 거치지 않는다.**

**조치**: 깊은 정규화. 화면에 그려지는 값은 전부 원시값으로 강제하고, 모르는 키는 버린다.
(`src/lib/journey-storage.js` — `text()` / `pickText()` / `normalizeCandidate()` /
`normalizeInterpretation()` / `normalizeCatOverrides()` / `normalizeForm2Rows()` /
`normalizeForm2Enabled()` / `normalizeFavorable()` / `normalizeCorrectionRow()`)
사전 조회(`RESPONSE_TYPES_BY_ID[id]`, `BASE_INFO_CATEGORIES_BY_ID[id]`)에도 보호를 붙였다.

**고친 뒤**: 같은 18가지 오염 × 6경로 = **108가지 모두 정상**.
단위 시험 11종을 `tests/tj.mjs` 에 붙였다.

## 3. 고치지 않은 것과 이유

### ① 서식 입력칸에 길이 제한이 없다

`Field` 와 `Blank` 에는 `maxLength` 가 없다. 성명에 5,000자를 넣을 수 있다.

**고치지 않은 이유**: §1-③ 을 고친 뒤로는 **값이 잘리지 않는다.** 길게 쓰면 장수가 늘 뿐이고,
쪽수 예고가 그 사실을 말한다. 여기에 새로 상한을 걸면 **이미 저장된 기록에서 값이 사라진다.**
서식은 사람이 손으로 채우는 종이를 대신하는 것이라, 우리가 임의로 정한 글자 수로
잘라 내는 쪽이 더 위험하다. 진단 서술과 회신 원문은 서버로 나가므로 상한이 있어야 하고, 실제로 있다.

### ② 두 탭에서 동시에 진행하면 나중 탭이 앞 탭의 저장을 덮어쓴다

**시도**: 탭1 에서 서식에 이름을 쓰고, 탭2 에서 진단에 서술을 썼다.
**결과**: 저장소에는 탭2 의 서술만 남았다(`{name:"", reason:"탭2서술"}`).
다만 탭1 을 새로고침하면 탭1 의 이름이 도로 보인다 — 화면을 떠날 때 자기 상태를 다시 쓰기 때문이다.
즉 **각 탭은 자기 것을 잃지 않지만, 두 탭의 작업이 합쳐지지는 않는다.**

**고치지 않은 이유**: 제대로 고치려면 탭 사이 상태 동기화(`storage` 이벤트 수신 + 병합)가 필요하다.
동결 직전에 저장 경로를 건드리는 것은 회귀 위험이 크고, 잘못 만들면 **입력 중에 화면이 남의 값으로
바뀌는** 더 나쁜 일이 생긴다. 한 탭에서 쓰는 것이 정상 사용이고, 각 탭이 자기 것을 유지하므로 둔다.

### ③ 오프라인에서 새로고침하면 브라우저의 오프라인 화면이 뜬다

서비스워커가 없다. 이미 연 상태에서 오프라인이 되면 앱 안의 이동은 **전부 정상**이고
후보 요청도 폴백으로 돌아간다. 새로고침만 안 된다.

**고치지 않은 이유**: 심사기간(9/7~9/11)에 캐시가 낡은 판을 붙잡는 사고가
오프라인 새로고침이 안 되는 것보다 훨씬 나쁘다. 서비스워커는 한번 잘못 배포하면
사용자 브라우저에 남아 되돌리기 어렵다. 넣지 않는다.

### ④ 불러오기가 거대한 파일을 그대로 받는다

18MB 파일(성명 300만자)을 불러오면 그대로 저장된다. 6초 걸리고, 죽지는 않는다.

**고치지 않은 이유**: 사용자 자신이 내보낸 파일을 자신이 되돌리는 경로다.
어느 화면도 죽지 않았고, 남의 파일을 강제로 여는 경로가 아니다.
여기에 상한을 걸면 정상적으로 큰 기록(서식 2 여러 벌)을 못 여는 쪽이 더 흔한 사고가 된다.

## 4. 시험하지 못한 것

- **아주 큰 API 응답(수백 KB 이상)**: 응답을 가로채 주입하는 도구(CDP `Fetch.fulfillRequest`)가
  큰 본문에서 멈춰 끝내 재보지 못했다. 다만 우리 서버는 `max_tokens: 2048` 로 제한하므로
  그만한 응답이 우리 API 에서 나올 수는 없다.
- **실제 브라우저 인쇄 대화상자를 띄운 채로의 조작**: 헤드리스에서는 대화상자가 뜨지 않는다.
  인쇄 미디어를 고정한 상태에서의 입력은 시험했고 정상이었다.
